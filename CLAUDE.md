# Maestra — Project Instructions

Maestra is a full salon management platform (booking, POS, inventory, reporting, marketing) built from scratch, with AI (Denise) handling back-office work. The full product spec lives in `docs/spec.md` — read it before starting any new module.

## Stack
- **App:** Next.js (App Router) + TypeScript, Tailwind CSS
- **Database + auth + storage:** Supabase (Postgres). Schema changes go through SQL migrations in `supabase/migrations/` — never edit the database by hand.
- **Hosting:** Vercel (preview deploy on every push)
- **Later phases:** Stripe (Connect + Terminal), Twilio (SMS), email provider, Claude API

## Non-negotiable rules
1. **Multi-tenant from day one.** Every table with salon data has a `business_id`. Supabase Row Level Security (RLS) is enabled on every table so one salon can never see another's data. Write an RLS policy with every new table.
2. **Never store card numbers.** All payment data stays in Stripe.
3. **Secrets live in environment variables only** (`.env.local`, Vercel env settings). Never commit keys. `.env.local` stays in `.gitignore`.
4. **All AI actions go through the AI action log.** AI proposes a change → it's stored with the reason → a human approves (or auto-mode applies it) → it can be undone.
5. **Denise never writes to or messages clients.** No AI-written text ever reaches a client, and Denise never sends anything to one. Human staff can write to clients freely (free text in Message client, as well as the quick-pick templates), within the consent rules and logged with who sent it. Messages the system sends by itself (confirmations, receipts, automations, Denise's move notices) use fixed templates only.
6. **Booking rules live in one place** (`lib/scheduling/`), used by the calendar, online booking and the AI. No duplicate scheduling logic in UI code.
7. **Times are stored in UTC** and shown in the location's timezone. Exception: recurring schedules (opening hours, working hours, one-off changes, time off) are local wall-clock times (minutes since midnight on local dates), so a 9:00 shift stays 9:00 across daylight saving. Convert between the two only with `lib/scheduling/time.ts` (`toLocal`, `fromLocal`). The hour the clocks skip in spring (2–3am) and repeat in autumn is a known gap, left as it is (`docs/backlog.md`).

## Core data model
Business → Location → Staff, Resource; Service, StaffService; Client; Appointment → AppointmentItem (service + staff + resource + times); Product, StockLevel, StockMovement; Sale, Payment; Notification; AiActionLog. See `docs/spec.md` for fields.

## How to work
- Build in thin slices: one feature per task, working end to end (database → API → UI).
- Write automated tests for every scheduling rule (no double-booking, processing gaps, staff hours, resource conflicts).
- Use the seed for realistic fake data. `supabase/seed.sql` (the default, loaded by `npx supabase db reset`): 1 business, 1 location, the team (owner, manager, front desk, seven stylists and an assistant, each with a login and most with a PIN; stylists on commission, the manager and front desk hourly), ~40 services with level prices, ~500 clients, products, forms and settings, and a clear calendar. `supabase/seed-demo.sql` (`npm run seed:demo`) adds a busy month on top: appointments, time off, blocked time, a waitlist, memberships (a Blowout Club and a Color Club, with members, some coming in today, one paused and one whose payment failed), birthdays and review links for automations, where online bookings came from, and weddings and events at every stage (an on-location wedding with a party of 6 among them), and, when it loads during opening hours, the moment Denise fixes, planted rather than left to chance (a colorist with a color client in the chair finishing in about 20 minutes, a client booked straight after and 20 minutes free after that; `planted` in the seed), then `supabase/seed-large.sql` adds a second, larger salon, Harbor & Vine (owner@, manager@ and frontdesk@harborvine.test; 35 stylists across hair, color, nails and skin, open seven days, about ten off any day, with sick, vacation and part-day time off around today, appointments from three days back to a week ahead, and two shared views) for trying the calendar at scale (`e2e/large-salon.spec.ts`). Never use real client data in development.
- Tests pass whatever day and time they run (the salon is closed Sundays and Mondays and in the evening): a test about "today" uses a fixed clock (`busyDay()` in `tests/db/helpers.ts`: the next day with demo visits, and 11am there, passed as `now`), opens today all day (`openAllDay`), or, for the Dashboard, moves the salon's world so a busy day is today (`busyToday` in `e2e/fixtures.ts`, the week test's time machine). A fixture at a set time on a seeded stylist calls `makeRoom` first, since the database refuses a double-booking with the demo calendar.
- Browser test files never depend on what earlier files (or runs) left behind: each makes its own clients, visits, products and suppliers, or sets the shared rows it reads to a known state first (7N's stock, Bridget's learned length, Harbor & Vine's seeded calendar order), and puts back what it changed in `afterAll` or `finally`. A file that sells, checks out or just opens a checkout calls `putBackSales()` (`e2e/fixtures.ts`): afterwards, the stock its sales took and gave back is put back and its sales, checkout drafts and payment links are removed. Saved settings a file changes (views, a person's zoom, automations, series) are put back the same way; derived rows the app makes by itself as pages are viewed (Denise's proposals, referral codes, insights) and logs are left. Dates are worked out from today, never written in.
- After each slice: run the linter, type check and tests, then summarize what changed and how to try it.
- **Every new or changed feature updates its help page in `docs/help/` in the same commit** (or adds one: one short page per task, format in `docs/help/README.md`), so Denise always knows how the current version works. Labels, screens and who can do it must match the code; `tests/unit/help.test.ts` checks every page parses and its button opens a real screen.
- Prefer simple, readable code over clever code. Ask before adding a new dependency.

## Commands
- `colima start` — start the Docker runtime that local Supabase needs (stop with `colima stop`)
- `npx supabase start` — start local Supabase (database, auth, Studio at http://127.0.0.1:54323)
- `npm run dev` — local app
- `npm run lint` / `npm run typecheck` / `npm test` — unit tests, no database needed
- `npm run test:db` — RLS and database tests; needs local Supabase running with the demo data (`npm run seed:demo`)
- `npm run test:e2e` — Playwright UI tests in `e2e/`; needs local Supabase with the demo data. Builds the app for production and runs it on port 3100 (build folder `.next-e2e`) with `ANTHROPIC_API_KEY` blanked, so tests never call the real Claude API; it's reused while it runs. A production build because the dev server's memory grows with every page until it crawls and its worker runs out of heap partway through a full run (and dev runs every effect twice); `E2E_DEV=1 npm run test:e2e e2e/<file>` uses the dev server instead, quicker for one file and with React's development checks. `MAESTRA_TEST_SERVER=true` opens the dev outbox on that build, only against a local database (`outboxOpen` in `lib/dev-outbox.ts`). The key is only ever blanked in a run's own server (its own port and build folder), never in `.env.local` or the dev server on 3000 (`tests/unit/api-key-isolation.test.ts`). Fails on any browser console error, which in dev includes Next.js dev overlay errors (a test that goes offline on purpose lets through only Chrome's own "Failed to load resource: net::ERR_INTERNET_DISCONNECTED" lines, `allowOfflineLogs`; our code catches the rest, with `reach` in `lib/reach.ts`; a test that opens a missing page on purpose lets through only React's error #419, `allowNotFoundLogs`). A failed test's error, screenshot, trace and error context are copied to `e2e/failures/<run>/` (git-ignored, `e2e/keep-failures.ts`) when the run ends, so a rerun never overwrites them. First time: `npx playwright install chromium`
- `npm run test:week` — plays a busy week at Maple & Ash (Tuesday to Saturday: bookings at the desk and online, a walk-in, an overrun and a call-out with Denise's fixes, no-shows and a late cancel with their fees, checkouts by card, cash, split and gift card, a promotion code, a return, a refund, a void and each night's close-out) and checks the calendar, Sales, Payroll, Inventory, Policy and Reports agree with what happened (`e2e-week/week.spec.ts`). Each night the salon's dates move back a day (`e2e-week/time-machine.ts`), so the next day is today. Resets the local database to the default seed first (asks, or `-- --yes`), runs its own server on port 3300 (`.next-week`) and puts the demo data back after (`-- --keep` leaves the week to look around)
- `npx supabase db reset` — rebuild local database from migrations + the default seed (clear calendar)
- `npm run insights` — recalculate what Denise has learned for every salon (prints counts only)
- `npm run eval:denise` — asks Ask Denise 44 real front desk, owner and stylist questions (15 of them "how do I…" from the help guide) with the **real** Claude API against the demo data and checks tools, facts, permissions and privacy (`evals/denise.eval.ts`; costs tokens: ask the user first). `EVAL_DRY=1 npm run eval:denise` checks the cases without calling the API
- `npm run screenshots` — marketing screenshots of Maple & Ash for the pitch deck, plus every main screen for before-and-after comparisons, in `screenshots/` (git-ignored; `scripts/screenshots.ts`; `-- --out=<folder>` elsewhere, `-- --reuse --build` rebuilds the app over the same data, and `node scripts/polish-pairs.ts <before> <after> <out>` puts pairs side by side): resets the local database (asks first, or `-- --yes`; `-- --reuse` retakes them without resetting or building), loads the demo data as of a busy moment on the latest open day (the seed, insights, app server and browser share one clock, `scripts/demo-clock.ts`), builds for production on port 3200 (`.next-screenshots`) and drives Chromium at 1440×900, 2×. Shot 04 calls the **real** Claude API (and fix explanations do, with the key set). Run `npm run seed:demo` after to get the usual data back
- `npm run seed:demo` — reset, then add the busy demo history (16 weeks back, nine days ahead, with actual times and retail sales) (`supabase/seed-demo.sql`) and the large salon (`supabase/seed-large.sql`), both loaded with `psql` in the database container; the tests need it
- `npm run db:types` — regenerate `lib/database.types.ts` after a migration
- `npm run backup:drill` — dumps the local database like a backup, restores it into a scratch database and checks every table, policy and function came back (counts only), then checks the photo backup with a test file of its own; see `docs/operations.md` for backups and restores
- `npm run photos -- backup | restore [prefix] | verify` — the Storage file backup (`lib/photo-backup.ts`): copy now, put back missing files, or check every file has an identical copy
- `npm run jobs -- configure [app url] | status | run <job> | off` — the scheduled jobs the database runs (pg_cron): where the app is and the `CRON_SECRET`, kept in Vault; never prints the secret
- `npm run release:demo` — a safe release to the public demo (https://maestra-demo.vercel.app, `scripts/release-demo.ts`), stopping at the first failure: main checked out, clean and pushed (and the demo branch able to move forward to it, `.env.demo.local` there, the live site answering); lint, types, unit tests and `npm run test:week`; `demo:db -- migrate` and `demo:db -- check` (RLS on every table) on the demo's database; `demo:db -- reset` if a seed changed since the last release; then the `demo` branch (Vercel's production branch for the demo) pushed to main's commit, a wait until `/api/demo/status` reports that commit, and `npm run test:demo` against the live site. Until the push the live demo keeps its code (a failure says whether its database was touched); after it, a failure says how to roll back (Vercel's Instant Rollback)
- `npm run import:phorest:dry-run` — calls the **real** Phorest API (GET only) with the `PHOREST_*` credentials in `.env.local`, maps everything and prints only record counts and mapping issues; saves nothing. Ask the user before running it. `-- --months-back=N --months-ahead=N` sets the appointment range (default 24 and 12)

## Phorest importer (`lib/import/phorest/`)
- **Read-only toward Phorest.** All requests go through `http.ts`, which only sends GET (enforced in `readOnlyFetch`, proved by `tests/unit/phorest/http.test.ts`). Never add another way to call Phorest.
- **Never print or log** Phorest credentials, the business ID, or any record values. Report problems through `IssueLog` (entity, field, reason, count: no values) and errors as status + endpoint template.
- Modules under `lib/import/` and `lib/scheduling/` run under plain Node (for the dry-run script), so relative imports use explicit `.ts` extensions and avoid TypeScript-only runtime syntax (enums, parameter properties).

## Actual times
- Each service on a visit records when it really started, went into processing, came back to the chair and finished (`appointment_items.started_at`, `processing_started_at`, `processing_ended_at`, `finished_at`), and visits record `checked_in_at` / `checked_out_at`. The visit flow is Check in → Check out: booking details' one primary action, in a footer pinned to the bottom of the panel, is "Check in" for booked visits and "Check out" once checked in (`nextStep` in `lib/visit-times.ts`, front of house only), with its status as text in the header ("Checked in at 9:56am", or "In service since 10:52am" when the stylist tapped it, `visitStatusText`); everything else is in the "⋯" menu next to it (Running late, Edit booking, Undo check-in, Mark no-show, Undo no-show, Cancel booking). Mark no-show asks first (here and on Denise's not-arrived card, "Yes, no-show"), then offers Undo on the toast for 10 seconds, and "Undo no-show" in "⋯" after (`undoNoShow` in `lib/scheduling/book.ts`: the visit's time is checked against the booking rules again, since a no-show frees it, then `undo_no_show` puts back what it was, booked or confirmed, with the calendar version; logged in `appointment_events` as `no_show` / `no_show_undone`). There are no timing taps in booking details. A service's own times (Start service, Processing, Back in chair, Finish service, Undo) are optional taps for the stylist on **My day** (`/my-day`, their phone view, `components/service-timer.tsx`), one at a time through `record_item_time` (Start service checks the client in; "undo" takes back the last tap). A check-in made by mistake is taken back with "Undo check-in" in booking details, or Undo on the toast for 10 seconds after checking in (front of house; `undo_check_in`: back to booked, the times tapped in since cleared, logged in `appointment_events` with who did it). Not after checkout: booking details says to void the sale (managers and owners), with a link to it.
- **Status changes are instant:** check in, no-show, cancel, and their undos (booking details, the toast's Undo, Denise's not-arrived card) show on the block and in booking details at once (`setStatusNow` in `board.tsx`, held until the day shows them), save in the background without reloading the page in the action (`changeVisitStatus` and friends don't revalidate), then the day reloads behind it (`router.refresh()`); a save that fails puts it back and says why (booking details' message, or the calendar's notice) (`e2e/calendar-day.spec.ts`, "shows at once"). The calendar page loads in rounds of queries run together (`app/calendar/page.tsx`), never one after another.
- The demo data gives each stylist their own pace on some services, a few late, no-show-prone and retail-buying clients, and clients on their own visit cycles, so there's real history to learn from. Every visit is checked in and out; Bridget, Gil and Shae tap their times on My day (all but about one visit in ten), and Hannah, Nola, Sandra and Lois never do, so their figures come from check-in to checkout.

## What Denise learns (`lib/insights/`)
- **Our code calculates every fact; Claude never does.** Pure functions (unit-tested; they run under plain Node, so relative `.ts` imports): `durations.ts` (each stylist × service: median actual time, middle-half spread and consistency, visits counted after setting aside outliers, trusted from 5 visits, trend faster or slower (only when it's statistically meaningful: 5 minutes or 8%, Mann-Kendall |z| ≥ 3, 12+ visits with 5 in the last 60 days), overrun rate, and a suggested length when it's 10+ minutes off the menu). Two kinds of data, never mixed in one figure (`basis`): `tapped` (the stylist's own start and finish on My day) and `check_in_out` (check-in to checkout, only for checked-out visits with one service and no taps, in `compute.ts` `measured`). Estimates count for less: trusted from 10 visits (`MIN_ESTIMATED_VISITS`), no trends, a suggestion only 15+ minutes off the menu, 15+ minutes over for the risk check, and half weight (`ESTIMATE_WEIGHT`) in the salon's running-over figures, which say how much of them is estimated (`estimatedShare`). Each stylist × service takes the tapped figure when it's trusted, else the trusted estimate, else whichever has more to go on. Whenever it matters, Denise and the pages say a number is "based on check-in to checkout times" (`BASIS_TEXT`, `visitsText`: the booking panel's usual-length note, the Durations page, the risk headline, Ask Denise's tools and system prompt), `clients.ts` (usual gap, next due, due status, favorite stylist, weekday and time of day, usual services, late / cancel / no-show / retail rates, spend, churn risk), `salon.ts` (busiest and quietest hours, overruns by service and weekday and who runs over, no-shows by day and time, rebooking rate per stylist).
- **Denise uses it:** a stylist can have their own length for a service (`staff_services` active/processing/finishing; `timingFor` / `stretchTiming` in `lib/scheduling/booking.ts`; new bookings take it, `private.stylist_timing` in the database). The booking panel warns when a service is booked shorter than the stylist usually takes and offers their usual length for that booking (`minutes` on a line, saved as the item's own timing). The **Durations** page (`/durations`, owners and managers) shows learned vs. booked lengths and applies Denise's suggestion in one click through the AI action log (feature `duration`, `apply_duration_action` / `undo_duration_action`). The **risk check** (`lib/denise/risk.ts`) turns visits likely to run over (the stylist usually takes 10+ minutes longer, or 15+ when that's from check-in to checkout) into `likely_overrun` disruptions for the resolver, so fixes are proposed before it happens; it runs in every scan and in its scheduled job twice a night (`/api/cron/risk`, recorded with `record_ai_proposals_as_system`), and these don't pop her panel open. The **morning brief** (`lib/denise/brief.ts`: risks, likely no-shows, regulars due back with nothing booked, low stock for today's services, clients coming in with credit) is on the Dashboard, laid out in sections from our own numbers (no Claude wording). The **client insight card** (`components/client-insight.tsx`, wording in `lib/insights/describe.ts`) is on client profiles and at checkout; booking details has her one-line version (`components/client-insight-line.tsx`).
- `compute.ts` loads a salon's last year and stores the results in `insights` (kinds `duration`, `client`, `client_spend`, `salon`), written only with the service role. It runs nightly (`/api/cron/insights`, one of the scheduled jobs the database runs: see Scheduled jobs below), with `npm run insights` (also at the end of `npm run seed:demo`), and after each checkout for that visit (`recomputeForVisit`, in `after()`). RLS: front of house reads everything; stylists read their own durations, client habits and salon patterns, never spend.

## Scheduling (`lib/scheduling/`)
- `availability.ts`: when a staff member can work (opening hours, shifts, one-off changes, approved time off).
- `booking.ts`: whether an appointment item can be booked (`checkItem`, `checkAppointment`), with a reason code for each problem. Processing time is free for the stylist but not for the chair or room. Any code that creates or moves appointments must check here first. The database enforces the same two clashes underneath (migration `…_no_double_booking_in_the_database.sql`): exclusion constraints on `appointment_items` (`staff_busy`, the service and finishing parts; `resource_held`, the whole item), deferred to commit, for visits that hold time (`holds_time`, not canceled or no-show, kept by triggers). A clash it catches (23P01) is treated like a stale calendar: checked again, then refused with the usual reason. Imported records (`imported`) are kept as they came, clashes and all, for Denise; moving one makes it count. Tests that set visits up directly give them their own time or stylist (`throwawayStylist` in `tests/db/helpers.ts`).
- `load.ts`: loads schedules and a `BookingContext` from Supabase for those checks.
- `blocks.ts`: blocked time (lunch, break, training, meeting, personal), one-off or repeating on weekdays, in wall-clock minutes (`time_blocks`, with `time_block_skips` for days taken out). The booking rules treat each occurrence like another client: the stylist's busy time can't overlap it (processing can). Moving one day of a repeating block (`move_time_block`) skips that day and adds a one-off. Denise's resolver may move a lunch or break by up to 30 minutes as part of a fix (never training, meetings or personal time); the move is in the proposal (`block_moves`) and undo puts it back.
- `series.ts` / `series-book.ts`: recurring appointments (`appointment_series`; each visit is an ordinary appointment with `series_id` and `series_index`). `planSeries` checks every date and suggests alternatives (nearest time that day, another stylist, a nearby day); `bookSeries` saves visit by visit through `saveBooking`. Edits, drag-moves and cancellations apply to this visit, this and following, or all (`visitsInScope`). Booking a series, and changing or moving visits in scope, is all or nothing (`saveVisits` → `saveBookings` in `book.ts` → `save_appointments`, one transaction that also creates the series or group): ones that don't fit are reported and nothing is saved. Other visits' items are matched to the edited visit's lines by service (`matchItems`, from each line's `itemId`), so each keeps its own booked length. A new date in Edit booking moves the visits in scope by the same number of days (`changeSeries` `days`).
- `patch-tests.ts`: whether a client's patch tests cover a service that needs one (`services.requires_patch_test`), by the salon's rules (`businesses.patch_test_*`). With enforcement `block`, `saveBooking` refuses with a `patch_test` problem; otherwise `lib/client-checks.ts` (`visitWarnings`) warns in the booking panel. Booking details shows "Before this visit (2)" only while something's outstanding, one collapsed row under the visit that opens to the checklist (`checklist`: a row per patch test (`patchStatus`: "Patch test — none on file") and per form the visit needs (`requiredForms` in `lib/forms.ts`: "Color consent — not signed"), each with its action (Record patch test, Fill it in now) and whether it holds the visit up; done rows show a check and fade; hidden once all done). Check in warns once, listing everything outstanding ("Check in anyway" / "Not yet"). With enforcement `block`, the database refuses to take a visit past booked (check-in, Start service, or checkout straight from booked) while a required patch test isn't in order (trigger `appointments_patch_test_on_arrival`, `private.patch_tests_missing`, the same rule as `patchTestState`; errcode 55000, hint `patch_test`); a manager or owner can check the client in anyway with a reason (`check_in_patch_override`, `checkInPatchOverride`), logged in `appointment_events` (kind `patch_test_override`, with who, why and the services) and shown on the checklist row. Nothing about either on the calendar block.
- `move-day.ts`: moving a visit to another day and/or time (booking details' "⋯" → Move to another day, `moveVisitTo`; or a new Date in Edit booking): every service moves together with its stylist, shifted in local days and minutes (`shiftStart`, `daysBetween` in `time.ts`, so 2pm stays 2pm across daylight saving), each through `saveBooking`; a series by scope, a group as a whole (`moveGroupItem`, checked across both days) or not at all. If it doesn't fit, Denise's nearest times that day with the same stylist (`bookingIdeas`). The calendar then goes to that day with the visit open (`openOn` in `board.tsx`). Week view (drag onto a day) is still to come.
- Notices for staff moves: every change staff make to a visit's day, time or stylist (Edit booking, drags, Move to another day, for series and groups too) records a notice to the client and each stylist involved, like Denise's fixes (`lib/move-notices.ts` snapshots before and compares after; `moveNotices` in `lib/notifications.ts`, fixed templates `visit_moved` / `staff_visit_moved`, saying the day unless it's today; `record_visit_notices`, front of house, the visit's own client and the salon's staff only). Recorded in `notifications` until texts are connected; a notice that can't be recorded never undoes the move.
- `waitlist.ts`: free time, the opening a cancellation, no-show or applied Denise fix leaves (`openingAround`), waitlist clients who fit it (`matchOpening`: asked for the stylist first, then longest waiting), and the next free qualified stylist for walk-ins (`nextFree`, `walkInQueue`). Loading and booking live in `lib/waitlist-load.ts` and `lib/waitlist-book.ts` (through `saveBooking`). Denise shows openings in her panel; staff book and contact the client.
- `groups.ts` / `group-book.ts`: group bookings (`appointment_groups`; each guest is an ordinary appointment with `group_id`). `checkGroup` checks all guests together; `bookGroup` books everyone or no one and `moveGroupItem` moves the whole party by the same amount, each in one transaction (`saveBookings`); `changeGroupStatus` cancels everyone. The resolver keeps groups together when they fit within about an hour (`GROUP_SPLIT_MINUTES` in `resolve.ts`).
- `book.ts`: the only way to book, edit or move appointments, and to change their status or notes. It checks the rules, then saves through the database functions `save_appointment`, `set_appointment_status` and `set_appointment_notes`, which record who made the change. Appointments and items can't be written directly (no RLS write policies). A per-location `calendar_version` stops two people booking the same slot at once: a save checked against an out-of-date calendar is refused and re-checked.

## Denise (the AI assistant)
- Denise (short for DNIS, Digital Navigator of Issues and Scheduling) is the name for the AI everywhere in the app. She speaks in first person, briefly and warmly. Art is in `public/brand/denise/` (`wave`: nothing to do, `think`: working, `point`: presenting a fix, `face`: small icon). Periwinkle is her color, only for her messages, suggestions and badge; navy (from the Maestra logo) is the app's main color.
- `lib/scheduling/ai-actions.ts` is the AI action log: Denise records proposals (`recordProposals`, up to 3 ranked options per problem, keyed by a subject like `overrun:<id>`), and staff apply, reject or undo them (`applyAction`, `rejectAction`, `undoAction`). Applying and undoing check the booking rules (`checkMoves`, `checkAppointment`) first, then call the database functions `apply_ai_action` / `undo_ai_action`, which check nothing changed since, record the exact previous state and restore it. Only booked and confirmed visits are ever moved. The `ai_actions` table can't be written directly.
- `lib/scheduling/disruptions.ts`: staff report a visit running over or a client running late (`reportRunningLate`: which one depends on whether the client has checked in) and a stylist out for the rest of the day (`reportCallOut`, which also adds approved time off). Stored in `schedule_disruptions`.
- `lib/scheduling/resolve.ts` (pure): `findConflicts` applies the reports to the day (`effectiveCalendar`), finds overruns, late clients, call-outs and double-bookings, and searches for up to 3 fixes each, ranked by fewest clients moved, then the smallest delay (a stylist change counts as 30 minutes). It never moves checked-in or finished visits, or anyone earlier or into the past, and every option passes `checkMoves`.
- `lib/denise/`: `scan.ts` loads a day, finds conflicts, words them (`wording.ts`, first person) and records them as proposals with the notifications they'd send (`lib/notifications.ts`: fixed templates for clients, never AI text). `fixes.ts` approves (re-checking the rules against the day with its reports), rejects and undoes. Notifications are only recorded in `notifications` for now; nothing is sent.
- **Denise everywhere** (`components/denise-chat/`): one conversation per signed-in person (`store.ts`: a module store, so it carries over as pages change, and sessionStorage `maestra:denise:<staff>` for reloads, the last 40 messages), shown by `DeniseChat` (`chat.tsx`). Every staff page gets her bubble from `AppShell`/`AppFrame` (`DeniseBubble` in `bubble.tsx`: her face in the bottom right corner, opening a panel that docks beside the page from md up, so it never covers the page's own buttons, and fills the screen on a phone); the calendar has her in its side panel instead (`AppShell denise={false}`), the same conversation, with no Ask bar on top: her message box gives an example naming someone on the team who does cuts ("Find a haircut with Gil after 1 PM", `askExample` in `board.tsx`; `DeniseChat` `placeholder`, and "Find a haircut after 1 PM" in her bubble for those who can book); the checkout has her button in its top bar (`DeniseHeaderButton`), docked beside the ticket and payment, which stack by container query (`@3xl`) when there's too little room, so Complete sale is never under her. ⌘K / Ctrl+K opens her anywhere with the cursor in her box (`useDeniseShortcut`, `focusDenise`). Not on client-facing pages (booking site, client account, pay and card links). She knows the page (`lib/denise/page.ts`: `pageOf` from the path and the visit open on the calendar; `pageContext` finds the client with the asker's own access): on a client's profile, a checkout, a sale or an open visit, Ask Denise gets `this_client` (`Knowledge.client`: their habits and next visits, first name only) and a line in her system prompt. The Dashboard's Ask bar asks in her bubble.
- On the calendar (`app/calendar/denise-panel.tsx`, `denise-actions.ts`): the right panel is closed until something opens it (an appointment, a new booking, a new conflict or reorder, a question for Denise) and closes with X, Escape or a click on empty calendar space; while closed, Denise's face sits in the corner with a badge that bounces for anything new. Her panel holds only what to act on now: fixes, waitlist openings, reorders, and clients not arrived 15 minutes after their start (`lateNotices` in `scan.ts`: one card, a row each with the client's full name (never cut off) and their due time under it, small Open and Mark no-show buttons below, and dismiss as an X in the row's top right corner, suggesting a call or a no-show; dismissed ones stay gone for the day). Her art is `components/denise.tsx` (`DenisePose`, `DeniseFace`); colors are the `denise-*` tokens.
- Claude (`lib/denise/claude.ts`, `@anthropic-ai/sdk`) is used only when `ANTHROPIC_API_KEY` is set. **Our code calculates every fact; Claude never calculates or invents numbers**: it gets facts from our functions, decides what matters, explains, answers and proposes. That includes dates: her facts give them with the weekday already worked out ("Sat, Oct 24", `sayDate` in `knowledge.ts`), never a bare date for Claude to work a weekday out from. Models: `claude-haiku-5-5` (`CHAT_MODEL`) for chat and fix explanations, `claude-sonnet-5-5` (`ANALYSIS_MODEL`) for "why"/compare questions (`modelFor`).
- "Ask Denise" (`lib/denise/assistant.ts`, context built by `lib/denise/context.ts`) has tools that call our functions: `find_openings` (availability, with the booking rules, checking each stylist with their trusted usual time for the service (`findOpenings` `timings`) and saying which length was used), `propose_booking` (with the same length, carried in the proposal's `timing` to `apply_ai_action`), `propose_fixes` (her scan, recording fixes to approve), `how_to` (the help guide, below), and read-only lookups from `lib/denise/knowledge.ts`: `client_insights`, `overdue_clients`, `stylist_durations`, `salon_patterns`, `day_schedule`, `inventory_levels`, `sales_summary`, `events_in_month`, `event_balance`. Voice and style (in the system prompt): she speaks for herself (never "the tool" or "the system"), plain text, no gendered pronouns for anyone, two to four sentences, lists as the top 3 with "Want the rest?". The pages are read at runtime (`lib/help/load.ts`; `outputFileTracingIncludes` ships them with `/api/denise`).

The meter (`metered`) must call the SDK's methods on `client.messages`, never detached (`tests/unit/denise-errors.test.ts` runs the real SDK against a stand-in network). Wherever she is (`components/denise-chat/store.ts`) she shows "Denise is thinking…" with live status at once, "Still working on it…" after 20 seconds, and takes one question at a time. - Privacy: send Claude only what a question needs: first names (never last names, phone numbers, emails, addresses, allergies, notes or payment details) and scheduling facts. Never log the key.

Tests use a fake client and the browser tests' server has no key; no test calls the real API. `npm run eval:denise` runs 44 real questions (15 of them how-to questions answered from the help guide) against the demo data (real API, costs tokens: ask first).

## Checkout and sales (`lib/checkout.ts`, `lib/sales.ts`, `app/sales/`)
- Tables `sales`, `sale_items` (services and products, each with its share of the discount, its tax and total), `sale_tips` (per stylist), `payments` (cash with tendered/change, card recorded as taken on the salon's own terminal: last 4 or approval code only, never a card number; `processor` / `processor_reference` are for Stripe later; negative amounts are refunds and voids) and `sale_events` (every step, with who and why). Front of house reads them; stylists don't; nobody writes directly.
- `complete_sale` (front of house) checks out a visit or sells retail on its own in one go: every service on the visit at its booked price (a changed price needs a reason), products out of stock, a discount (amount or %, with a reason, by `businesses.discount_roles`, the front desk up to `discount_max_percent`), tax per line (`tax_rate_services_bp`, `tax_rate_retail_bp`), tips, and payments that add up to the total exactly; the visit is then checked out (service products deducted as before). `private.price_sale` shares the discount and rounds tax exactly as `computeSale` in `lib/checkout.ts` (tests check they agree).
- `void_sale` and `refund_sale` are for owners and managers, with a reason: voids reverse every payment, put products back and reopen the visit; refunds never exceed what was paid and can return products (back in stock or not) and a gift card, package or membership the sale sold (`private.refund_line_value`, `refundable_lines`: a gift card only for its unused balance, then cancelled; a package only for its unused sessions, then cancelled; a membership ended today, for the period less the services it covered). Money for those comes back only by returning them. Each refund records what went back and the money for each (`sale_events.returned`; `cancel_package` too). ## Cancellation policy (`lib/policy.ts`, `lib/policy-billing.ts`, `lib/policy-visits.ts`, `/settings/policies`, `/policy`, `app/card/[token]/`, migration `…_cancellation_policy.sql`)

- **Fees charge themselves.** A trigger on the visit's status (`private.assess_policy_fee`) records a fee (`policy_fees`, one per visit, with `policy_fee_events`) on a no-show or a late cancel by the client (`CLIENT_CANCEL_REASONS`; the salon canceling never costs the client, and refunds their deposit), less any deposit, pending for 10 minutes (`CHARGE_GRACE_MINUTES`) so Undo no-show voids it; without a card it waits (`no_card`) until one is added. `runPolicyCharges` (service role: every 15 minutes at `/api/cron/fees`, "Charge due fees now" for owners, and Try the card again) claims due fees, charges the card with an idempotency key, records it (`record_fee_charge`), and sends the receipt through the outbox (`feeReceipt`); a failure notifies owners, managers and the front desk (`policy_fee_failed`) and shows on the Dashboard ("Fees that didn't go through"). Waiving (`waive_policy_fee`, the roles in `waive_roles`, a reason always) works before or after; a charged fee is refunded.
- Where it shows: booking details (the card on file, strikes, the fee and its controls, the fee in the no-show and cancel confirmations), the client profile ("Cancellation policy": the card and consent, Remove card, Send card link, their fees), the online booking review and manage pages, and **Policy** (`/policy`, owners and managers, Sales group): recovered, charged, waived, failed, card-on-file share of the next 30 days, the month's incidents and repeat offenders (`lib/policy-report.ts`, pure). (`late_cancellations`, front of house, first names, amounts only for owners and managers). Test cards only until Stripe is connected.

## Inventory
- Tables: `suppliers`, `products` (brand, line, shade/name, SKU, barcode, type `retail` / `back_bar`, unit `g` / `ml` / `unit`, container `size`, cost, retail price, shelf), `stock_levels` (on hand, reorder point and quantity, per location) and `stock_movements` (every change with its reason: `service_use`, `sale`, `count`, `order_received`, `adjustment`, and the amount after it).
- Amounts are in the product's unit, so back-bar color is tracked in grams or ml, partly used tubes included; retail is in whole units. `lib/inventory.ts` has the formatting, value, low-stock, filter and form helpers.
- On hand only changes through `private.move_stock`, called by the database functions for each flow (`adjust_stock` for sales and adjustments; later stages add service use, orders and counts). Stock levels and movements can't be written directly.
- Color usage (`lib/color-usage.ts`): a formula entry can be tied to a service on a visit (`client_formulas.appointment_item_id`) and list products and amounts (`formula_products`), recorded with `add_formula` from the appointment panel or the client profile. Services have default recipes (`service_products`, set with `set_service_recipe`). Checking a visit out runs `private.deduct_item_stock` for each service: the latest formula with products, or else the recipe. It moves only the difference from what's already been taken, so formulas recorded or corrected after checkout put stock right.
- Ordering (`lib/purchase-orders.ts`, `/inventory/orders`): `purchase_orders` go draft → sent → partly received → received. Owners and managers write (`save_purchase_order`), send and delete drafts; the front desk receives (`receive_purchase_order`), which adds containers × size to stock as `order_received` movements and records the cost paid as the product's cost. Low stock (below the reorder point) is flagged on the Inventory page and the Dashboard.
- Denise's reorders (`lib/denise/reorder.ts`, pure forecast in `lib/inventory-forecast.ts`): from stock on hand and on order, and what the next two weeks of bookings will use (the visit's formula, else the client's latest for that service, else their latest color formula, else the recipe), she suggests one order per supplier, recorded in the AI action log (feature `reorder`). A manager approves it into a draft order (`apply_reorder_draft`, undo with `undo_reorder_draft` until it's sent); nothing is ordered automatically.
- Stocktakes (`lib/stocktake.ts`, `/inventory/count`, made for a tablet): owners and managers count shelf by shelf (full containers plus the open one's grams or ml). Each count snapshots the expected amount when it's entered, so sales or service use afterwards aren't counted against it. Finishing applies the differences as `count` movements; products not counted stay as they are. Missing stock worth $15+ or a fifth of what's expected is flagged as possible shrinkage.
- Permissions: owners and managers manage everything; the front desk sells retail and receives orders; stylists record formulas and view stock (`canManageInventory`, `canSellRetail`, `canReceiveOrders`). The database enforces the same.
