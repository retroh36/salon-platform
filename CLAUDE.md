# Maestra — Project Instructions

Maestra is a full salon management platform (booking, POS, inventory, reporting, marketing) built from scratch, with AI (Denise) handling back-office work. The full product spec lives in `docs/spec.md` — read it before starting any new module.

## Stack
- **App:** Next.js (App Router) + TypeScript, Tailwind CSS
- **Database + auth + storage:** Supabase (Postgres). Schema changes go through SQL migrations in `supabase/migrations/` — never edit the database by hand.
- **Hosting:** Vercel (preview deploy on every push)
- **Later phases:** Stripe (Connect + Terminal), Twilio (SMS), email provider, Claude API

## Non-negotiable rules
1. **Multi-tenant from day one.** Every table with salon data has a `business_id`. Supabase Row Level Security (RLS) is enabled on every table so one salon can never see another's data. Write an RLS policy with every new table.
2. **Never store card numbers.** All payment data stays in Stripe.
3. **Secrets live in environment variables only** (`.env.local`, Vercel env settings). Never commit keys. `.env.local` stays in `.gitignore`.
4. **All AI actions go through the AI action log.** AI proposes a change → it's stored with the reason → a human approves (or auto-mode applies it) → it can be undone.
5. **AI never chats with clients.** Client messages use approved templates only.
6. **Booking rules live in one place** (`lib/scheduling/`), used by the calendar, online booking and the AI. No duplicate scheduling logic in UI code.
7. **Times are stored in UTC** and shown in the location's timezone. Exception: recurring schedules (opening hours, working hours, one-off changes, time off) are local wall-clock times (minutes since midnight on local dates), so a 9:00 shift stays 9:00 across daylight saving. Convert between the two only with `lib/scheduling/time.ts` (`toLocal`, `fromLocal`).

## Core data model
Business → Location → Staff, Resource; Service, StaffService; Client; Appointment → AppointmentItem (service + staff + resource + times); Product, StockLevel, StockMovement; Sale, Payment; Notification; AiActionLog. See `docs/spec.md` for fields.

## How to work
- Build in thin slices: one feature per task, working end to end (database → API → UI).
- Write automated tests for every scheduling rule (no double-booking, processing gaps, staff hours, resource conflicts).
- Use the seed for realistic fake data. `supabase/seed.sql` (the default, loaded by `npx supabase db reset`): 1 business, 1 location, the team (owner, manager, front desk and seven stylists, each with a login; stylists on commission, the manager and front desk hourly), ~40 services with level prices, ~500 clients, products, forms and settings, and a clear calendar. `supabase/seed-demo.sql` (`npm run seed:demo`) adds a busy month on top: appointments, time off, blocked time, a waitlist, memberships (a Blowout Club and a Color Club, with members, some coming in today, one paused and one whose payment failed), birthdays and review links for automations, and where online bookings came from. Never use real client data in development.
- After each slice: run the linter, type check and tests, then summarize what changed and how to try it.
- **Every new or changed feature updates its help page in `docs/help/` in the same commit** (or adds one: one short page per task, format in `docs/help/README.md`), so Denise always knows how the current version works. Labels, screens and who can do it must match the code; `tests/unit/help.test.ts` checks every page parses and its button opens a real screen.
- Prefer simple, readable code over clever code. Ask before adding a new dependency.

## Commands
- `colima start` — start the Docker runtime that local Supabase needs (stop with `colima stop`)
- `npx supabase start` — start local Supabase (database, auth, Studio at http://127.0.0.1:54323)
- `npm run dev` — local app
- `npm run lint` / `npm run typecheck` / `npm test` — unit tests, no database needed
- `npm run test:db` — RLS and database tests; needs local Supabase running with the demo data (`npm run seed:demo`)
- `npm run test:e2e` — Playwright UI tests in `e2e/`; needs local Supabase with the demo data. Runs its own dev server on port 3100 (build folder `.next-e2e`) with `ANTHROPIC_API_KEY` blanked, so tests never call the real Claude API; it's reused while it runs. Fails on any browser console error, which includes Next.js dev overlay errors. First time: `npx playwright install chromium`
- `npx supabase db reset` — rebuild local database from migrations + the default seed (clear calendar)
- `npm run insights` — recalculate what Denise has learned for every salon (prints counts only)
- `npm run eval:denise` — asks Ask Denise 34 real front desk, owner and stylist questions (10 of them "how do I…" from the help guide) with the **real** Claude API against the demo data and checks tools, facts, permissions and privacy (`evals/denise.eval.ts`; costs tokens: ask the user first). `EVAL_DRY=1 npm run eval:denise` checks the cases without calling the API
- `npm run seed:demo` — reset, then add the busy demo history (16 weeks back, nine days ahead, with actual times and retail sales) (`supabase/seed-demo.sql`, loaded with `psql` in the database container); the tests need it
- `npm run db:types` — regenerate `lib/database.types.ts` after a migration
- `npm run backup:drill` — dumps the local database like a backup, restores it into a scratch database and checks every table, policy and function came back (counts only), then checks the photo backup with a test file of its own; see `docs/operations.md` for backups and restores
- `npm run photos -- backup | restore [prefix] | verify` — the Storage file backup (`lib/photo-backup.ts`): copy now, put back missing files, or check every file has an identical copy
- `npm run jobs -- configure [app url] | status | run <job> | off` — the scheduled jobs the database runs (pg_cron): where the app is and the `CRON_SECRET`, kept in Vault; never prints the secret
- `npm run import:phorest:dry-run` — calls the **real** Phorest API (GET only) with the `PHOREST_*` credentials in `.env.local`, maps everything and prints only record counts and mapping issues; saves nothing. Ask the user before running it. `-- --months-back=N --months-ahead=N` sets the appointment range (default 24 and 12)

## Phorest importer (`lib/import/phorest/`)
- **Read-only toward Phorest.** All requests go through `http.ts`, which only sends GET (enforced in `readOnlyFetch`, proved by `tests/unit/phorest/http.test.ts`). Never add another way to call Phorest.
- **Never print or log** Phorest credentials, the business ID, or any record values. Report problems through `IssueLog` (entity, field, reason, count: no values) and errors as status + endpoint template.
- Modules under `lib/import/` and `lib/scheduling/` run under plain Node (for the dry-run script), so relative imports use explicit `.ts` extensions and avoid TypeScript-only runtime syntax (enums, parameter properties).

## Actual times
- Each service on a visit records when it really started, went into processing, came back to the chair and finished (`appointment_items.started_at`, `processing_started_at`, `processing_ended_at`, `finished_at`), and visits record `checked_in_at` / `checked_out_at`. The visit flow is Check in → Check out: booking details' one primary action, in a footer pinned to the bottom of the panel, is "Check in" for booked visits and "Check out" once checked in (`nextStep` in `lib/visit-times.ts`, front of house only), with its status as text in the header ("Checked in at 9:56am", or "In service since 10:52am" when the stylist tapped it, `visitStatusText`); everything else is in the "⋯" menu next to it (Running late, Edit booking, Undo check-in, Mark no-show, Cancel booking). There are no timing taps in booking details. A service's own times (Start service, Processing, Back in chair, Finish service, Undo) are optional taps for the stylist on **My day** (`/my-day`, their phone view, `components/service-timer.tsx`), one at a time through `record_item_time` (Start service checks the client in; "undo" takes back the last tap). A check-in made by mistake is taken back with "Undo check-in" in booking details, or Undo on the toast for 10 seconds after checking in (front of house; `undo_check_in`: back to booked, the times tapped in since cleared, logged in `appointment_events` with who did it). Not after checkout: booking details says to void the sale (managers and owners), with a link to it.
- The demo data gives each stylist their own pace on some services, a few late, no-show-prone and retail-buying clients, and clients on their own visit cycles, so there's real history to learn from. Every visit is checked in and out; Bridget, Gil and Shae tap their times on My day (all but about one visit in ten), and Hannah, Nola, Sandra and Lois never do, so their figures come from check-in to checkout.

## What Denise learns (`lib/insights/`)
- **Our code calculates every fact; Claude never does.** Pure functions (unit-tested; they run under plain Node, so relative `.ts` imports): `durations.ts` (each stylist × service: median actual time, middle-half spread and consistency, visits counted after setting aside outliers, trusted from 5 visits, trend faster or slower (only when it's statistically meaningful: 5 minutes or 8%, Mann-Kendall |z| ≥ 3, 12+ visits with 5 in the last 60 days), overrun rate, and a suggested length when it's 10+ minutes off the menu). Two kinds of data, never mixed in one figure (`basis`): `tapped` (the stylist's own start and finish on My day) and `check_in_out` (check-in to checkout, only for checked-out visits with one service and no taps, in `compute.ts` `measured`). Estimates count for less: trusted from 10 visits (`MIN_ESTIMATED_VISITS`), no trends, a suggestion only 15+ minutes off the menu, 15+ minutes over for the risk check, and half weight (`ESTIMATE_WEIGHT`) in the salon's running-over figures, which say how much of them is estimated (`estimatedShare`). Each stylist × service takes the tapped figure when it's trusted, else the trusted estimate, else whichever has more to go on. Whenever it matters, Denise and the pages say a number is "based on check-in to checkout times" (`BASIS_TEXT`, `visitsText`: the booking panel's usual-length note, the Durations page, the risk headline, Ask Denise's tools and system prompt), `clients.ts` (usual gap, next due, due status, favorite stylist, weekday and time of day, usual services, late / cancel / no-show / retail rates, spend, churn risk), `salon.ts` (busiest and quietest hours, overruns by service and weekday and who runs over, no-shows by day and time, rebooking rate per stylist).
- **Denise uses it:** a stylist can have their own length for a service (`staff_services` active/processing/finishing; `timingFor` / `stretchTiming` in `lib/scheduling/booking.ts`; new bookings take it, `private.stylist_timing` in the database). The booking panel warns when a service is booked shorter than the stylist usually takes and offers their usual length for that booking (`minutes` on a line, saved as the item's own timing). The **Durations** page (`/durations`, owners and managers) shows learned vs. booked lengths and applies Denise's suggestion in one click through the AI action log (feature `duration`, `apply_duration_action` / `undo_duration_action`). The **risk check** (`lib/denise/risk.ts`) turns visits likely to run over (the stylist usually takes 10+ minutes longer, or 15+ when that's from check-in to checkout) into `likely_overrun` disruptions for the resolver, so fixes are proposed before it happens; it runs in every scan and in its scheduled job twice a night (`/api/cron/risk`, recorded with `record_ai_proposals_as_system`), and these don't pop her panel open. The **morning brief** (`lib/denise/brief.ts`: risks, likely no-shows, regulars due back with nothing booked, low stock for today's services, clients coming in with credit) is on the Dashboard, laid out in sections from our own numbers (no Claude wording). The **client insight card** (`components/client-insight.tsx`, wording in `lib/insights/describe.ts`) is on client profiles and at checkout; booking details has her one-line version (`components/client-insight-line.tsx`).
- `compute.ts` loads a salon's last year and stores the results in `insights` (kinds `duration`, `client`, `client_spend`, `salon`), written only with the service role. It runs nightly (`/api/cron/insights`, one of the scheduled jobs the database runs: see Scheduled jobs below), with `npm run insights` (also at the end of `npm run seed:demo`), and after each checkout for that visit (`recomputeForVisit`, in `after()`). RLS: front of house reads everything; stylists read their own durations, client habits and salon patterns, never spend.

## Scheduling (`lib/scheduling/`)
- `availability.ts`: when a staff member can work (opening hours, shifts, one-off changes, approved time off).
- `booking.ts`: whether an appointment item can be booked (`checkItem`, `checkAppointment`), with a reason code for each problem. Processing time is free for the stylist but not for the chair or room. Any code that creates or moves appointments must check here first.
- `load.ts`: loads schedules and a `BookingContext` from Supabase for those checks.
- `blocks.ts`: blocked time (lunch, break, training, meeting, personal), one-off or repeating on weekdays, in wall-clock minutes (`time_blocks`, with `time_block_skips` for days taken out). The booking rules treat each occurrence like another client: the stylist's busy time can't overlap it (processing can). Moving one day of a repeating block (`move_time_block`) skips that day and adds a one-off. Denise's resolver may move a lunch or break by up to 30 minutes as part of a fix (never training, meetings or personal time); the move is in the proposal (`block_moves`) and undo puts it back.
- `series.ts` / `series-book.ts`: recurring appointments (`appointment_series`; each visit is an ordinary appointment with `series_id` and `series_index`). `planSeries` checks every date and suggests alternatives (nearest time that day, another stylist, a nearby day); `bookSeries` saves visit by visit through `saveBooking`. Edits, drag-moves and cancellations apply to this visit, this and following, or all (`visitsInScope`), each visit checked on its own; ones that don't fit are reported.
- `patch-tests.ts`: whether a client's patch tests cover a service that needs one (`services.requires_patch_test`), by the salon's rules (`businesses.patch_test_*`). With enforcement `block`, `saveBooking` refuses with a `patch_test` problem; otherwise `lib/client-checks.ts` (`visitWarnings`) warns in the booking panel. Booking details shows "Before this visit (2)" only while something's outstanding, one collapsed row under the visit that opens to the checklist (`checklist`: a row per patch test (`patchStatus`: "Patch test — none on file") and per form the visit needs (`requiredForms` in `lib/forms.ts`: "Color consent — not signed"), each with its action (Record patch test, Fill it in now) and whether it holds the visit up; done rows show a check and fade; hidden once all done). Check in warns once, listing everything outstanding ("Check in anyway" / "Not yet"). With enforcement `block`, the database refuses to take a visit past booked (check-in, Start service, or checkout straight from booked) while a required patch test isn't in order (trigger `appointments_patch_test_on_arrival`, `private.patch_tests_missing`, the same rule as `patchTestState`; errcode 55000, hint `patch_test`); a manager or owner can check the client in anyway with a reason (`check_in_patch_override`, `checkInPatchOverride`), logged in `appointment_events` (kind `patch_test_override`, with who, why and the services) and shown on the checklist row. Nothing about either on the calendar block.
- `waitlist.ts`: free time, the opening a cancellation, no-show or applied Denise fix leaves (`openingAround`), waitlist clients who fit it (`matchOpening`: asked for the stylist first, then longest waiting), and the next free qualified stylist for walk-ins (`nextFree`, `walkInQueue`). Loading and booking live in `lib/waitlist-load.ts` and `lib/waitlist-book.ts` (through `saveBooking`). Denise shows openings in her panel; staff book and contact the client.
- `groups.ts` / `group-book.ts`: group bookings (`appointment_groups`; each guest is an ordinary appointment with `group_id`). `checkGroup` checks all guests together; `bookGroup` books everyone or no one; `moveGroupItem` moves the whole party by the same amount (checked as one change first); `changeGroupStatus` cancels everyone. The resolver keeps groups together when they fit within about an hour (`GROUP_SPLIT_MINUTES` in `resolve.ts`).
- `book.ts`: the only way to book, edit or move appointments, and to change their status or notes. It checks the rules, then saves through the database functions `save_appointment`, `set_appointment_status` and `set_appointment_notes`, which record who made the change. Appointments and items can't be written directly (no RLS write policies). A per-location `calendar_version` stops two people booking the same slot at once: a save checked against an out-of-date calendar is refused and re-checked.

## Denise (the AI assistant)
- Denise (short for DNIS, Digital Navigator of Issues and Scheduling) is the name for the AI everywhere in the app. She speaks in first person, briefly and warmly. Art is in `public/brand/denise/` (`wave`: nothing to do, `think`: working, `point`: presenting a fix, `face`: small icon). Periwinkle is her color, only for her messages, suggestions and badge; navy (from the Maestra logo) is the app's main color.
- `lib/scheduling/ai-actions.ts` is the AI action log: Denise records proposals (`recordProposals`, up to 3 ranked options per problem, keyed by a subject like `overrun:<id>`), and staff apply, reject or undo them (`applyAction`, `rejectAction`, `undoAction`). Applying and undoing check the booking rules (`checkMoves`, `checkAppointment`) first, then call the database functions `apply_ai_action` / `undo_ai_action`, which check nothing changed since, record the exact previous state and restore it. Only booked and confirmed visits are ever moved. The `ai_actions` table can't be written directly.
- `lib/scheduling/disruptions.ts`: staff report a visit running over or a client running late (`reportRunningLate`: which one depends on whether the client has checked in) and a stylist out for the rest of the day (`reportCallOut`, which also adds approved time off). Stored in `schedule_disruptions`.
- `lib/scheduling/resolve.ts` (pure): `findConflicts` applies the reports to the day (`effectiveCalendar`), finds overruns, late clients, call-outs and double-bookings, and searches for up to 3 fixes each, ranked by fewest clients moved, then the smallest delay (a stylist change counts as 30 minutes). It never moves checked-in or finished visits, or anyone earlier or into the past, and every option passes `checkMoves`.
- `lib/denise/`: `scan.ts` loads a day, finds conflicts, words them (`wording.ts`, first person) and records them as proposals with the notifications they'd send (`lib/notifications.ts`: fixed templates for clients, never AI text). `fixes.ts` approves (re-checking the rules against the day with its reports), rejects and undoes. Notifications are only recorded in `notifications` for now; nothing is sent.
- On the calendar (`app/calendar/denise-panel.tsx`, `denise-actions.ts`): the right panel is closed until something opens it (an appointment, a new booking, a new conflict or reorder, a question for Denise) and closes with X, Escape or a click on empty calendar space; while closed, Denise's face sits in the corner with a badge that bounces for anything new. Her tab shows glowing blocks and dashed previews of where a fix would move them, only while her panel is open on a fix (gone once it closes, she moves on, or the fix is applied or dismissed; her badge is the only lasting signal), Apply / Dismiss / Undo, and "Running late" (appointment panel) and "Out for the day" (stylist header menu). Her panel holds only what to act on now: fixes, waitlist openings, reorders, and clients not arrived 15 minutes after their start (`lateNotices` in `scan.ts`: one card, a row each with the client's full name (never cut off) and their due time under it, small Open and Mark no-show buttons below, and dismiss as an X in the row's top right corner, suggesting a call or a no-show; dismissed ones stay gone for the day). Her reorders are one card too ("2 reorders ready to review": a line per supplier with its number of products and total, and one "Review on Inventory" button). The morning brief is on the Dashboard. Her art is `components/denise.tsx` (`DenisePose`, `DeniseFace`); colors are the `denise-*` tokens.
- Claude (`lib/denise/claude.ts`, `@anthropic-ai/sdk`) is used only when `ANTHROPIC_API_KEY` is set. **Our code calculates every fact; Claude never calculates or invents numbers**: it gets facts from our functions, decides what matters, explains, answers and proposes. Models: `claude-haiku-5-5` (`CHAT_MODEL`) for chat and fix explanations, `claude-sonnet-5-5` (`ANALYSIS_MODEL`) for "why"/compare questions (`modelFor`).
- "Ask Denise" (`lib/denise/assistant.ts`, context built by `lib/denise/context.ts`) has tools that call our functions: `find_openings` (availability, with the booking rules, checking each stylist with their trusted usual time for the service (`findOpenings` `timings`) and saying which length was used), `propose_booking` (with the same length, carried in the proposal's `timing` to `apply_ai_action`), `propose_fixes` (her scan, recording fixes to approve), `how_to` (the help guide, below), and read-only lookups from `lib/denise/knowledge.ts`: `client_insights`, `overdue_clients`, `stylist_durations`, `salon_patterns`, `day_schedule`, `inventory_levels`, `sales_summary`. Permissions live in `knowledge.ts`: stylists see their own durations, regulars and rebooking, and no money; sales are for owners and managers; `propose_fixes` for the front of house. It never writes to the database: proposals go through the AI action log for staff to approve. Claude never writes messages to clients. Voice and style (in the system prompt): she speaks for herself (never "the tool" or "the system"), plain text, no gendered pronouns for anyone, two to four sentences, lists as the top 3 with "Want the rest?".
- **How to use Maestra** (`docs/help/`, `lib/help/`): the help guide, one short page per task for front desk staff (front matter: title, keywords, `who` can do it, and `open`, the screen it starts on with its button label; then numbered steps and "Good to know"). Denise's `how_to` tool searches it (`searchHelp`, `howTo`) and she answers "How do I…?" only from the page it returns, as numbered steps, with the page's button under her answer ("Open new sale", `HelpLink`, a plain link). If the person asking can't do it (`who`), she gets no steps or button and says who can; if no page matches, she says it isn't in the guide rather than guessing. The pages are read at runtime (`lib/help/load.ts`; `outputFileTracingIncludes` ships them with `/api/denise`).
- **Denise always responds.** Reports and cancellations go through her streaming endpoint (`app/api/denise/route.ts`, one JSON event per line: status steps, her answer word by word, then her reply and her view of the day), as do questions. Whatever triggers her, she replies (`lib/denise/respond.ts`, facts from `lib/denise/triggers.ts`): the fixes she found, why there's nothing to do ("Gil's day is already over… nothing to move"), or what staff can do when there's no fix (`noFixAdvice`); failures are logged as one `[denise]` line (`lib/denise/errors.ts`: what she was doing, the error's name, message and our stack frames, and for API errors the status, error type and request id; never the question or client data), and she says what staff can do (`failureKind`: the daily limit, back tomorrow; the API busy, rate limited or unreachable, try again in a minute; a setup problem or our bug, logged, with a reference like "Ref D-7KQ2M9" that matches the log line). Failed tools and fix explanations are logged the same way. The meter (`metered`) must call the SDK's methods on `client.messages`, never detached (`tests/unit/denise-errors.test.ts` runs the real SDK against a stand-in network). On the calendar (`use-denise.ts`) she shows "Denise is thinking…" with live status at once, "Still working on it…" after 20 seconds, and takes one question at a time. Her panel opens for a trigger unless someone is mid-task in the side panel; then her badge calls. A booking the rules refuse gets her nearest times that work, one click away (`lib/denise/ideas.ts`, `bookingIdeas`).
- Privacy: send Claude only what a question needs: first names (never last names, phone numbers, emails, addresses, allergies, notes or payment details) and scheduling facts. Never log the key.
- Cost and reliability: every call goes through `metered` (`lib/denise/usage.ts`): tokens logged per salon in `ai_usage` (`record_ai_usage`, service role), and at the salon's daily limit (`businesses.ai_daily_token_limit`, set on Settings, which shows usage) Denise falls back to template wording. Without the key, over the limit, or if the API fails, everything still works with template wording. Tests use a fake client and the browser tests' server has no key; no test calls the real API. `npm run eval:denise` runs 34 real questions (10 of them how-to questions answered from the help guide) against the demo data (real API, costs tokens: ask first).

## Checkout and sales (`lib/checkout.ts`, `lib/sales.ts`, `app/sales/`)
- Tables `sales`, `sale_items` (services and products, each with its share of the discount, its tax and total), `sale_tips` (per stylist), `payments` (cash with tendered/change, card recorded as taken on the salon's own terminal: last 4 or approval code only, never a card number; `processor` / `processor_reference` are for Stripe later; negative amounts are refunds and voids) and `sale_events` (every step, with who and why). Front of house reads them; stylists don't; nobody writes directly.
- `complete_sale` (front of house) checks out a visit or sells retail on its own in one go: every service on the visit at its booked price (a changed price needs a reason), products out of stock, a discount (amount or %, with a reason, by `businesses.discount_roles`, the front desk up to `discount_max_percent`), tax per line (`tax_rate_services_bp`, `tax_rate_retail_bp`), tips, and payments that add up to the total exactly; the visit is then checked out (service products deducted as before). `private.price_sale` shares the discount and rounds tax exactly as `computeSale` in `lib/checkout.ts` (tests check they agree).
- `void_sale` and `refund_sale` are for owners and managers, with a reason: voids reverse every payment, put products back and reopen the visit; refunds never exceed what was paid and can return products (back in stock or not). Receipts print (`/sales/<id>?print=1`) or go by email through the outbox (`outbox_messages.html`).
- `complete_sale` also takes services added at checkout (`service_id` + `staff_id` + `quantity`, priced by `private.stylist_price`), a stylist on each service and product line (product credit, for commission), a discount per line (`discount: {kind, value, reason}`, stored as `line_discount_cents` / `line_discount_reason`; line and sale discounts together count against the limits), `draft_id` (completes that draft) and `rebook_appointment_id` (the same client's next visit, booked at checkout). An out-of-stock product needs an owner or manager, or their OK on the draft (`approve_stock_override` → `stock_overrides`).
- `/sales` lists a day's sales with money in by tender. Tax, discount and receipt settings: `/settings/checkout` (owners). Receipts group lines by stylist with a subtotal each (`receiptGroups`). Denise's sales figures (`salesBetween`) and the Dashboard's week come from these tables; the demo seed gives every checked-out visit its sale (retail credited to the visit's stylist, and many rebooked).

## Text-to-pay (`lib/payment-links.ts`, `app/pay/[token]/`, migration `…_payment_links.sql`)
- From checkout, "Text a payment link instead" (a client on the sale, nothing paid yet) sends the client a link by text (or email) to the number on file (editable), through the outbox, in a fixed message (`linkMessage`, never AI-written). The link holds the ticket as sent (`linkSnapshot`: what `complete_sale` is sent, the lines and totals to show, who can be tipped) and works once, for 24 hours (`LINK_HOURS`; `payment_links`, only the token's hash stored; one open per checkout; `create_payment_link`, front of house). While it's out, the checkout waits ("Waiting for payment", the ticket can't be changed, checking every few seconds), with "Cancel the link" to change the ticket or pay at the desk; completing the sale at the desk cancels any open link (a trigger).
- The link opens `/pay/<token>` (public, phone-first, in the salon's brand): the receipt with each line, a tip for each stylist (18/20/25% of their services, custom, or none; `parseTips`), the card (the test provider's test cards in test mode) and Pay. The card is charged through the payment provider layer, then `complete_payment_link` (service role) completes the sale through `complete_sale` as the staff member who sent the link (every rule checked again), marks the card payment as taken online (`processor`), and the visit is checked out; if that fails, the charge is refunded. Expired, canceled or paid links say so. Back at the desk, the checkout shows "Paid by link" with the total and tips.

## Gift cards (`lib/gift-cards.ts`, `app/gift-cards/`, migration `…_gift_cards.sql`)
- `gift_cards` (purchased or promotional, active or voided, balance, optional expiry, who it's for, physical or digital) and `gift_card_events` (sold, issued, imported, redeemed, reloaded, refunded, adjusted, voided: signed amount, balance after, sale, who, why). Balances change only through the database functions; the front of house reads cards, stylists don't.
- Codes: a card sold digitally gets 16 characters from 31 that can't be mixed up (no 0/O, 1/I/L), about 79 bits (`private.new_gift_code`), shown as `K7QM-3XRP-9TWD-FH2C`; a physical card keeps its own code (8 to 32 letters and digits, entered or scanned). `lookup_gift_card` is logged in `gift_card_lookups` and limited to 30 per staff member per 10 minutes.
- At checkout (`complete_sale`): sell (`gift_card` lines, $5 to $1,000, the salon's presets or any amount; untaxed, never discounted; digital ones are emailed in the salon's colors through the outbox), reload (`gift_card_reload`, purchased cards only), and redeem (`gift_card` payments, any part of the balance). Gift cards can't be bought with a gift card. Voids put redeemed money back and void unused cards sold on the sale; refunds can go back onto the card. Promotional cards (`issue_promo_card`, managers) expire, can't be reloaded and are never refunded as money. Managers adjust and void cards with a reason (`adjust_gift_card`, `void_gift_card`).
- `/gift-cards`: check a balance, recent cards (bought and promotional), each card's history; `/settings/gift-cards` (owners): presets, expiry (default none) and promotional expiry, with a note that gift card rules vary by state. Phorest vouchers map to purchased cards with their remaining balance (`import_gift_card`, service role; codes that are too short or shared get new ones).

## Packages (`lib/packages.ts`, migration `…_packages.sql`)
- Owners set up `package_templates` (services and counts, price, optional expiry in months, optional stylist levels) on `/settings/packages` (`save_package_template`). Selling one at checkout (`package` line, needs a client, taxed like services) gives the client their own `client_packages` with `client_package_items` (total, used, and what one use is worth: the price shared by menu prices, for refunds and reports).
- Redeeming: a service line with `package_item_id` uses one (right client, level and service, not expired, a use left); it isn't taxed or discounted again, and the database adds a `package` payment for it, so staff's payments cover only the rest. The checkout ticks it by default when the client's package covers the service (`packageFor`: the soonest-expiring first), and the booking form points it out ("Ava has 3 Blowouts left on a package"). Voids give uses back and cancel unused packages sold on the sale; package uses are never refunded as money.
- Managers cancel a package with a reason (`cancel_package`), refunding what the unused uses are worth (`proRatedRefund`) by card or cash on the sale that sold it, or nothing. Every step is in `package_events`. Packages and uses left show on the client profile and in Denise's client card (`withPackages`); everyone at the salon can see them.

## Memberships (`lib/memberships.ts`, `lib/memberships-load.ts`, `lib/memberships-billing.ts`, `lib/payments/`, migration `…_memberships.sql`)
- Owners set up plans on Settings → Memberships (`save_membership_plan`, `parsePlanForm`): price and how often (every n weeks or months), services included each period (`membership_plan_services`, each rolling over or not: one period's worth at most), member discounts on services and retail (whole percents), a minimum term (periods), notice to end (days), and whether and how long it can be paused. A membership copies the price and terms when it's sold (`client_memberships`), so plan changes affect new members only; included services come from the plan at each period's start (`membership_credits`).
- Sold at checkout ("Membership" under the lines: the plan, and the card it renews on; a `membership` line in `complete_sale`, needing a client; the first period is paid there, `private.start_membership`). Benefits apply by themselves while it's active: member prices come off services and retail before any staff discount (the best of the client's active memberships; `member_discount_cents`, never counted against staff discount limits; `Rates.member`, `memberDiscountOf` in `lib/ticket.ts` mirror it), and a service it includes is paid with a `membership` payment, untaxed (`membership_credit_id`; ticked by default when the checkout starts, like packages; "Membership" under Payment). Voids give included services back and cancel a membership sold on the sale (unless it's been used or renewed; `private.on_sale_voided`, a trigger); a voided renewal leaves it past due. Membership services, like package uses, can't be refunded as money.
- Billing (`runMembershipBilling`, service role: nightly at `/api/cron/memberships` (a scheduled job), "Run renewals now" for owners, and straight after a card update, a retry or a resume): `advance_membership` applies the day's changes (an ending, a pause starting, a pause ending), then a due payment goes through the membership's payment provider and `record_membership_charge` records it: a renewal sale (a `membership` line, a card payment with `processor`, so close-out shows it as "Card online") and the next period, anchored on the start date so the 31st doesn't drift (`addInterval`, as `private.add_interval`); or a failure: past due (no benefits), retried after 1, 3 and 4 more days (`RETRY_DAYS`), each with a notice to owners and managers (`notifications`, email, recorded until email is live) and on the Dashboard ("Membership payments that failed"); the fourth failure ends it. It can't record a payment that isn't due, so runs never charge twice.
- Front of house on the client profile ("Membership": what's included this period, when it renews or ends, history): pause from the end of the paid period for up to the plan's limit, resume (a new period from today, charged then), end at the earliest the rules allow (`earliestEnd`: a period's end after the minimum term and notice; or today for owners and managers), keep it, update the card, try a failed payment again. Booking details shows "Blowout Club member · Blowout: 2 left · 10% off retail" (or a failed payment), and the block's tooltip "Blowout Club member". Reports (owners): members, monthly recurring revenue (active and past due, as a monthly amount), joined and churn for the period (of the members at its start, how many ended), by plan (`membershipReport`).
- **The payment provider layer** (`lib/payments/`): `PaymentProvider.charge` with an idempotency key, and `refund`; a test provider for now (no money moves; test cards: …4242 works, …0002 is declined, …9995 has insufficient funds), and Stripe to plug in (`currentProvider` picks it once `STRIPE_SECRET_KEY` is set; until it's written, its charges fail with "Stripe isn't connected yet"). Cards are provider tokens (`payment_method_ref`, shown as "Visa …4242"), never numbers. Staff see "Test mode" wherever a card is chosen.

## Marketing automations (`lib/automations.ts`, `lib/automations-run.ts`, `lib/automations-load.ts`, `/settings/automations`, migration `…_automations.sql`)
- Four, each off until an owner turns it on (Settings → Automations): **rebook reminder** (a client past their usual return, `due` "overdue" from what Denise has learned, by the set number of days, with nothing booked: checked live), **win-back** (no visit for the set weeks, nothing booked), **birthday** (on the day or days before, with an optional offer; `clients.birth_month`/`birth_day` on the client form, Feb 29 on Feb 28 in other years) and **review request** (the set hours after checkout, with the salon's Google and Yelp links, `businesses.google_review_url`/`yelp_url`; at most one a month per client).
- **Templates only, never AI-written.** Owners edit the subject and message with a live preview (as a text and as an email, for a sample client); our code fills in `{first_name}`, `{salon}`, `{booking_link}` (the booking site with `?src=<kind>`), `{stylist}`, `{offer}`, `{review_links}` (`TEMPLATE_FIELDS`, `renderTemplate`); anything else in braces stops it going on (`automationProblems`, also: online booking must be on for a booking link, a review link for review requests, timing in range).
- **Consent and opt-outs.** Only clients who said yes to texts (`sms_opt_in`) or marketing email (`email_opt_in`) get them, by the preferred channel if they said yes to it, else the other (`channelFor`). Every message ends with an opt-out (`withOptOut`: "Reply STOP or tap …" / "Unsubscribe: …"), a link to the public `/unsubscribe/<token>` page (a button, so email link checkers can't opt anyone out; `marketing_opt_out`, service role; only the token's hash is stored), which turns off that channel for the client. Sent only between 9am and 8pm at the salon (`canSendAt`); at most one rebook, win-back or birthday message per client a week (`QUIET_DAYS`).
- **Sending** (`runAutomations`, service role): hourly at `/api/cron/automations` (a scheduled job) and "Send due messages now" for owners. Each message is recorded once per client per occasion (`marketing_messages`, unique `client_id, kind, cycle_key`: "rebook:<due date>", "birthday:<year>", "review:<visit>"), then put in `outbox_messages` (`/dev/outbox`) until Twilio and email are connected.
- **Results** per automation (last 90 days): sent, booked from it (the client booked within 14 days after, any way; each booking credited once, to the message before it), revenue (those visits' sales, less tax, tips and refunds) and opted out (`automationResults`).
- **Denise's suggestions** (`suggestAutomations`, from the salon's own numbers, worded by our code): shown on the page as proposals in the AI action log (feature `automation`, subject `automation:<kind>`; only for automations ready to turn on as they are). An owner turns one on (`apply_automation_action`, with Undo for a day: `undo_automation_action`) or says not now (she doesn't suggest it again). Owners and managers can see automations and what was sent; only owners change them.

## Payroll (`lib/payroll.ts`, `lib/payroll-load.ts`, `/payroll`, migration `…_payroll.sql`)
- Owners and managers (Sales → Payroll): for a pay period, each person's service and retail sales (after discounts, before tax), commission, tips, scheduled hours (their hours less approved time off, up to today) and total pay; each name drills into every ticket behind it (`PayTickets`), and "Export CSV" (`/payroll/export`, `payrollCsv`, a row per person in dollars, spreadsheet-formula safe) is for the payroll provider. The pay period is set per salon on Settings → Payroll (`businesses.pay_period`: weekly or biweekly from `pay_period_anchor`, semi-monthly 1st–15th and 16th–end, or custom), with Previous/Next and custom dates; the page opens on the last period that's over.
- **Rates are history, not settings.** Rates are set per person on Team → Schedule (`staff_compensation`: service and retail %, and `hourly_rate_cents` for anyone paid by the hour); every change is kept with when it took effect (`staff_compensation_history`, by a trigger, with who changed it; someone's first rates cover everything before them). Each service and product line with a stylist records the rate in effect when it's sold (`sale_items.commission_pct`, a trigger), and commission is paid from those (each line at its own rate, rounded once for the period); hourly pay uses the rate in effect each day (`hourlyPay`, `rateOn`). So changing a rate never changes past pay; the page shows the rates used ("45%, 50%" after a change).
- Refunds and voids: a sale counts in the period it was completed; a refund in the period it was given, taking back the same share of every line and tip (at the line's own rate); a void in the period it was voided, taking back what was left (`ticketsFor`). Nothing is paid twice; a sale voided in its own period nets to zero.
- Data comes only through `payroll_sales` (security definer): owners and managers get everyone; anyone else only themselves, with only their own lines and tips. Stylists see their own earnings on **My day** ("My earnings": this period so far, or the last one, with their tickets; no links into sales). The front desk sees no payroll.

## Your data and backups (`lib/data-export.ts`, `lib/zip.ts`, `lib/csv.ts`, `/settings/data`, `docs/operations.md`)
- "Your data is yours": owners download everything (clients, visits, formulas, sales with lines, payments and tips, products, gift cards and their history, packages, services and the team) as CSV files in one zip with a README (Settings → Your data, a POST to `/settings/data/export`), loaded with their own login so RLS keeps it to their salon. Every download is logged first (`log_data_export` → `data_exports`, owners only; no log, no file) and listed on the page. CSV cells are spreadsheet-formula safe (`lib/csv.ts`, shared with payroll); the zip is our own small writer (no dependency).
- Backups are the hosted Supabase project's (a paid plan with Point-in-Time Recovery), documented with restore steps and the checks in `docs/operations.md`. Storage files (photos, logos) aren't in database backups, so they have their own: nightly, new and changed files are copied to a private backup bucket, ideally in a separate Supabase project (`PHOTO_BACKUP_SUPABASE_URL` / `PHOTO_BACKUP_SECRET_KEY`, else this project's `photo-backups` bucket, service role only); a file deleted here stays in the backup 30 days, then goes too (`lib/photo-backup.ts`, `npm run photos`).

## Scheduled jobs (`supabase/migrations/…_scheduled_jobs.sql`, `docs/operations.md`)
- The database runs them (pg_cron), so they work on Vercel's free plan; `vercel.json` has no crons. Each calls one of our endpoints, `/api/cron/<job>` (each refuses anything without `CRON_SECRET` as a bearer token), through pg_net (`private.run_scheduled_job`), with the app's address and the secret from Supabase Vault (`configure_scheduled_jobs`, service role; `npm run jobs -- configure`). Unconfigured (as locally), they do nothing.
- UTC: photo backup 07:00, insights 08:00, Denise's risk check 09:00 and again 12:00, memberships 10:00, automations every hour at :15 (each salon's 9am–8pm sending hours checked in the app). Appointment reminders don't exist yet; they come with texts.

## Inventory
- Tables: `suppliers`, `products` (brand, line, shade/name, SKU, barcode, type `retail` / `back_bar`, unit `g` / `ml` / `unit`, container `size`, cost, retail price, shelf), `stock_levels` (on hand, reorder point and quantity, per location) and `stock_movements` (every change with its reason: `service_use`, `sale`, `count`, `order_received`, `adjustment`, and the amount after it).
- Amounts are in the product's unit, so back-bar color is tracked in grams or ml, partly used tubes included; retail is in whole units. `lib/inventory.ts` has the formatting, value, low-stock, filter and form helpers.
- On hand only changes through `private.move_stock`, called by the database functions for each flow (`adjust_stock` for sales and adjustments; later stages add service use, orders and counts). Stock levels and movements can't be written directly.
- Color usage (`lib/color-usage.ts`): a formula entry can be tied to a service on a visit (`client_formulas.appointment_item_id`) and list products and amounts (`formula_products`), recorded with `add_formula` from the appointment panel or the client profile. Services have default recipes (`service_products`, set with `set_service_recipe`). Checking a visit out runs `private.deduct_item_stock` for each service: the latest formula with products, or else the recipe. It moves only the difference from what's already been taken, so formulas recorded or corrected after checkout put stock right.
- Ordering (`lib/purchase-orders.ts`, `/inventory/orders`): `purchase_orders` go draft → sent → partly received → received. Owners and managers write (`save_purchase_order`), send and delete drafts; the front desk receives (`receive_purchase_order`), which adds containers × size to stock as `order_received` movements and records the cost paid as the product's cost. Low stock (below the reorder point) is flagged on the Inventory page and the Dashboard.
- Denise's reorders (`lib/denise/reorder.ts`, pure forecast in `lib/inventory-forecast.ts`): from stock on hand and on order, and what the next two weeks of bookings will use (the visit's formula, else the client's latest for that service, else their latest color formula, else the recipe), she suggests one order per supplier, recorded in the AI action log (feature `reorder`). A manager approves it into a draft order (`apply_reorder_draft`, undo with `undo_reorder_draft` until it's sent); nothing is ordered automatically.
- Stocktakes (`lib/stocktake.ts`, `/inventory/count`, made for a tablet): owners and managers count shelf by shelf (full containers plus the open one's grams or ml). Each count snapshots the expected amount when it's entered, so sales or service use afterwards aren't counted against it. Finishing applies the differences as `count` movements; products not counted stay as they are. Missing stock worth $15+ or a fifth of what's expected is flagged as possible shrinkage.
- Permissions: owners and managers manage everything; the front desk sells retail and receives orders; stylists record formulas and view stock (`canManageInventory`, `canSellRetail`, `canReceiveOrders`). The database enforces the same.
